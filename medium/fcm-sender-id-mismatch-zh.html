每週一準時誤報的 FCM 告警——我追進 SDK 原始碼，然後給開源社群提了一個修正

一個 403 錯誤被 SDK 歸類成「憑證失敗」，害我們每週誤發服務級告警、無效 token 永遠清不掉。追到根源後，我把修正做好、測好，提給了 PHP 生態最多人用的 Firebase SDK。這篇記錄整個過程，以及我真正想要的：錯誤分類應該向官方 Firebase Admin SDK 看齊。

事情從一個「不會收斂」的告警開始

我們維護一個多租戶的 FCM 推播服務（Laravel），其中一個租戶每週一固定發送週報推播。從某一週開始，監控系統每週一早上準時響：FCM 認證失敗。值班的人檢查 service account 憑證——沒過期、沒被撤銷、專案設定也對。推播其實大部分都發成功了，告警卻週週再來。

拉出六週的資料後，模式很明顯：920 筆失敗全部來自約 168 個不重複的 token，每一筆都是同一種錯誤——HTTP 403 PERMISSION_DENIED，錯誤碼 SENDER_ID_MISMATCH。這不是憑證問題，是這批 token 根本屬於別的 Firebase 專案（典型情境：測試環境的 App 註冊出來的 token 混進了正式環境的名單）。這種 token 對我們的專案來說永遠發不到，正確的處置是把它標記失效、從名單移除，然後就沒有然後了。

但我們的系統既沒有移除它們，還每週為它們發告警。為什麼？

追進 SDK：兩個相反的問題，同一個例外

我們用的是 kreait/firebase-php——PHP 生態事實上的 Firebase Admin SDK，每月下載量超過百萬。追進它的 MessagingApiExceptionConverter，找到了根源：

case StatusCode::STATUS_UNAUTHORIZED:
case StatusCode::STATUS_FORBIDDEN:
    $convertedError = new AuthenticationError($message, previous: $previous);

401 和 403 被合併成同一個 AuthenticationError。而這兩個狀態碼背後，是兩個需要完全相反處置的問題：

  • 401 UNAUTHENTICATED——service account 憑證真的壞了（過期、被撤銷、專案錯誤）。這是服務級的設定問題：停止發送、通知維運、修憑證。
  • 403 + SENDER_ID_MISMATCH——這一顆 token 屬於別的專案。這是單一 token 的永久失效：記錄、移除、不需要任何人半夜起床。

我們的程式把 AuthenticationError 當成「我的憑證壞了」來處理——這個解讀完全合理，卻同時踩中兩個坑：(a) 誤發憑證告警，(b) 永遠不會把錯配的 token 清掉，所以同一批 token 每次活動都再失敗一次，永不收斂。

先止血：一個我自己都不喜歡的 workaround

資訊其實沒有丟——$e->getMessage() 是 "SenderId mismatch"，$e->errors() 裡也有完整的 errorCode。所以應用層可以自己分流：

} catch (AuthenticationError $e) {
    $text = strtolower(json_encode($e->errors()).' '.$e->getMessage());
    if (str_contains($text, 'sender') && str_contains($text, 'mismatch')) {
        // 單 token 永久失效：標記、移除
    } else {
        // 真的憑證問題：告警
    }
}

能用，但它依賴 FCM 錯誤訊息的措辭和 payload 的形狀——這兩樣 Google 都沒有給過契約保證。哪天錯誤訊息改個大小寫、換個說法，分流就靜悄悄地失效了。用字串比對來做例外分類，本質上是在替 SDK 補課。

我真正想要的：向官方 Firebase Admin SDK 看齊

這是我決定往上游提改進的核心理由。SENDER_ID_MISMATCH 不是什麼罕見的邊角案例——它就列在 FCM HTTP v1 的官方 ErrorCode 列表裡，而且每一個官方 Firebase Admin SDK 都把它獨立成可辨識的錯誤型別：

  • Node.js：錯誤碼 messaging/sender-id-mismatch，官方文件明確把它和 UNREGISTERED 並列為「應該從資料庫移除 token」的訊號。
  • Java：列舉值 MessagingErrorCode.SENDER_ID_MISMATCH。
  • Go：判斷函式 messaging.IsSenderIDMismatch()。

換句話說，官方 SDK 的錯誤分類是照「呼叫端需要的處置」設計的，而不是照 HTTP 狀態碼。kreait 自己其實也有同樣精神的先例——UNREGISTERED（404）就有獨立的 NotFound 例外，甚至能吐回出問題的 token。403 的 sender mismatch 沒理由是例外。一個非官方 SDK 最有價值的特質之一，就是行為和官方 SDK 對得起來：開發者在 Node 學到的錯誤處理心智模型，搬到 PHP 不應該失效。

動手修：一個新例外，向下相容

修正本身不大。新增一個 SenderIdMismatch 例外（和既有的 AuthenticationError、NotFound 同樣的結構），然後把 converter 的 403 分支拆開——偵測到 FCM 回應細節裡的 errorCode: SENDER_ID_MISMATCH（以官方訊息 "SenderId mismatch" 作備援判斷）就丟新例外，其餘 401/403 一律維持原樣：

case StatusCode::STATUS_FORBIDDEN:
    $convertedError = $this->isSenderIdMismatch($errors, $message)
        ? new SenderIdMismatch($message, previous: $previous)
        : new AuthenticationError($message, previous: $previous);

之後呼叫端就能用型別直接表達意圖，不用再猜字串：

try {
    $messaging->send($message);
} catch (SenderIdMismatch $e) {
    // token 屬於別的專案：永久失效，移除即可
} catch (AuthenticationError $e) {
    // 真的憑證問題：告警
}

因為其他 401/403 的行為完全不變，對現有使用者是向下相容的——只有想要新粒度的人會感覺到差異。連同三個單元測試、文件章節和 CHANGELOG，整包改動跑過完整品質關卡：單元測試 361 個全綠、PHPStan 零錯誤、PHP-CS-Fixer 和 Rector 都乾淨。

開源的最後一哩：先開 issue，不是先丟 PR

過程中有兩個小插曲值得記。第一，這個 repo 在 2026 年 1 月剛從 kreait 組織搬到 beste（套件名不變），在舊名字底下搜尋既有 issue 會直接失敗——確認「沒有人提過」這件事花的功夫比想像中多。第二，專案的 CONTRIBUTING.md 明白寫著：先跟維護者討論，再動手開 PR，避免任何人把時間花在無法合併的改動上。

所以我沒有直接丟 PR，而是開了一個 feature request——beste/firebase-php#1123——把問題、生產環境數據、官方 SDK 的對照、還有已經全綠的實作分支全部附上，表明維護者點頭就能立刻開 PR。尊重專案的流程，跟把程式寫對一樣重要。

帶走的三件事

  • 例外階層要照「處置」設計，不是照狀態碼。如果兩個錯誤需要相反的處理方式，它們就不該是同一個型別——不管它們的 HTTP 狀態碼有多接近。
  • 非官方 SDK 的錯誤分類，應該向官方 SDK 對齊。官方文件把 SENDER_ID_MISMATCH 和 UNREGISTERED 並列為「清 token」訊號是有原因的；生態系裡每一種語言的開發者都值得同一套心智模型。
  • 在應用層用字串比對分流例外，是 SDK 欠你一個型別的訊號。workaround 可以止血，但把修正提回上游，才是讓同一個坑不再有下一個受害者的方法。
