一個修不好的 FCM 告警，變成我人生第一次的開源貢獻

一個反覆出現、怎麼修都修不好的告警,最後發現問題不在我們的程式,而是在我們用的 SDK 裡。這篇記錄一個菜鳥工程師從「看不懂」到「追到原因」,到完成人生第一次開源貢獻的整個過程。

一切從一個很煩的告警開始

我在公司負責維護一個推播服務,用 Laravel 寫的,幫好幾個系統發 FCM 推播(就是手機 App 上會跳出來的那種通知)。其中一個系統會定期發推播給它的用戶。

然後,每次一發送,監控就會響:「FCM 認證失敗」。

第一次看到的時候我滿緊張的,認證失敗聽起來很嚴重,好像是我們連 Firebase 的鑰匙壞掉了。趕快去檢查 service account 憑證(可以想成我們跟 Firebase 溝通用的鑰匙)——沒過期、沒被撤銷、設定也都對。更奇怪的是,推播其實大部分都發成功了。

那到底在叫什麼?下一次發送,同一個告警,又來了。再下一次,還是來了。

把資料攤開來看,發現不太對勁

被吵了好幾次之後,我決定把失敗紀錄全部拉出來看。看完發現一個模式:累積下來 920 筆失敗,但來來去去都是同一批 token(token 就是每支手機安裝 App 之後拿到的「地址」,推播要靠它才知道送去哪),算一算大概只有 168 個不重複的。而且每一筆的錯誤都長一樣:

HTTP 403 PERMISSION_DENIED
errorCode: SENDER_ID_MISMATCH

我去查了 SENDER_ID_MISMATCH 是什麼意思,查到之後鬆了一口氣,但也更困惑了。它的意思是:這個 token 是別的 Firebase 專案發的,不是我們家的。最常見的原因是有人拿測試環境的 App 註冊出 token,結果混進了正式環境的名單。

這種 token 我們永遠發不到,它跟憑證一點關係都沒有。正確的做法很單純:把它標記成失效、從名單移掉,就結束了。不需要告警,更不需要有人緊張。

但我們的系統把它當成「認證失敗」在處理,所以每次發送都告警一次,而且因為沒人把這批 token 移掉,它們下一次還是會再失敗一次。無限迴圈。

為什麼我們會把它當成認證失敗?

我本來以為是我們自己的程式寫錯,結果追下去發現,我們 catch 到的例外是 AuthenticationError——「認證錯誤」。看到這個名字,誰都會覺得是憑證壞了吧?

我們用的是 kreait/firebase-php 這個套件。Firebase 官方沒有出 PHP 版的 Admin SDK,這個社群維護的套件就是 PHP 圈實質上的標準,每個月被下載超過一百萬次。我第一次點進它的原始碼(以前都只敢看文件),在一個叫 MessagingApiExceptionConverter 的檔案裡找到了這段:

case StatusCode::STATUS_UNAUTHORIZED:   // 401
case StatusCode::STATUS_FORBIDDEN:      // 403
    $convertedError = new AuthenticationError($message, previous: $previous);

原來如此。401 和 403 被轉成同一個例外了。

這兩個狀態碼乍看很像,但代表的事情差很多:

  • 401:你的鑰匙(憑證)真的壞了。整個服務都發不出去,要趕快通知人來修。
  • 403 + SENDER_ID_MISMATCH:鑰匙沒問題,只是「這一個 token」不是你們家的。把它移掉就好,其他推播完全不受影響。

一個要人半夜起床,一個完全不用。但因為 SDK 給的是同一個例外,我們的程式分不出來。

先止血:一個我自己都覺得心虛的 workaround

好消息是資訊沒有真的不見——例外的訊息裡有 "SenderId mismatch" 這串字,$e->errors() 裡也有完整的錯誤碼。所以我先在自己的程式裡用字串比對硬分:

} catch (AuthenticationError $e) {
    $text = strtolower(json_encode($e->errors()).' '.$e->getMessage());
    if (str_contains($text, 'sender') && str_contains($text, 'mismatch')) {
        // 是 token 的問題:標記失效、移除
    } else {
        // 是真的憑證問題:告警
    }
}

告警不再誤報了,token 也開始被清掉了。但說實話,這段程式我寫得很心虛——我是在用「錯誤訊息裡有沒有某幾個英文字」來判斷要不要叫醒工程師。哪天 Google 把訊息的措辭改一下,這段判斷就會默默失效,而且我完全不會發現。

去看別人家是怎麼做的

寫完 workaround 之後我一直覺得哪裡怪怪的:這麼常見的錯誤,不可能只有我們遇到吧?所以我去翻了 Firebase 官方的 Admin SDK(官方有出 Node.js、Java、Go 這些版本),看它們怎麼處理同一個錯誤。

結果每一個官方 SDK 都把 SENDER_ID_MISMATCH 獨立出來:

  • Node.js:有專門的錯誤碼 messaging/sender-id-mismatch,官方文件還直接把它跟「token 已註銷」並列,說看到這兩種就該把 token 從資料庫移掉。
  • Java:有 MessagingErrorCode.SENDER_ID_MISMATCH 這個列舉值。
  • Go:甚至有一個現成的判斷函式 IsSenderIDMismatch()。

看到這裡我才確定:不是我想太多,是 PHP 這邊真的少了這一塊。官方 SDK 分錯誤的方式,是照「你接到這個錯誤之後該做什麼」來分的,不是照 HTTP 狀態碼。而且 kreait 這個套件自己也有類似的先例——token 已註銷(404)就有專門的 NotFound 例外。那 sender mismatch 沒道理沒有。

我心裡的期望其實很簡單:我在 Node 文件學到的錯誤處理方式,搬到 PHP 應該也要能用。同一個 FCM 錯誤,不該因為換了一個語言,就從「有名字的錯誤」變成「跟憑證壞掉長一樣的錯誤」。

那就自己動手吧

改動本身出乎意料地小。加一個新的例外類別 SenderIdMismatch(照著套件裡其他例外的樣子寫),然後把 converter 裡 403 的那條路拆出來:如果回應裡帶著 SENDER_ID_MISMATCH 錯誤碼,就丟新的例外;其他的 401/403 通通維持原樣:

case StatusCode::STATUS_FORBIDDEN:
    $convertedError = $this->isSenderIdMismatch($errors, $message)
        ? new SenderIdMismatch($message, previous: $previous)
        : new AuthenticationError($message, previous: $previous);

這樣以後用的人就可以直接 catch 型別,不用再猜字串:

try {
    $messaging->send($message);
} catch (SenderIdMismatch $e) {
    // token 是別人家的:移除它就好
} catch (AuthenticationError $e) {
    // 憑證真的有問題:告警
}

因為其他 401/403 的行為完全沒變,舊的程式碼不會被影響。我補了三個單元測試、一段文件和 CHANGELOG,然後把專案的檢查全部跑過一輪:361 個單元測試全綠、PHPStan(靜態分析)零錯誤、程式碼風格檢查也都過。跑完那一刻真的滿有成就感的。

人生第一次開源貢獻,學到的兩課

這裡要老實說:這是我人生第一次給別人的開源專案提改進。以前我跟開源的關係,大概就是用別人的套件、順手按個 star,頂多把自己的小專案丟上 GitHub。要對一個每月被下載百萬次的專案說「我覺得你這裡可以更好」,光是想就手心冒汗。而且本來以為寫完程式就結束了,結果最後一哩路才是新手村。

第一課:先搜尋之前,確認你搜對地方。我想先確認沒有人提過一樣的問題,但怎麼搜都搜不到這個 repo——後來才發現它在 2026 年 1 月剛從 kreait 搬家到 beste 這個組織(套件名字沒變,所以我完全沒發現)。用舊名字搜,GitHub 會直接跟你說查無此 repo。

第二課:先讀 CONTRIBUTING.md,不要急著丟 PR。這個專案的貢獻指南第一條就寫:動手之前先跟維護者討論,免得任何人把時間花在不會被合併的改動上。所以我忍住了直接開 PR 的衝動,改成開一個 feature request——beste/firebase-php#1123——把問題、我們的生產數據、官方 SDK 的對照,還有已經寫好測好的分支連結全部附上,跟維護者說:你點頭我就開 PR。

現在就是等回覆的狀態。就算最後沒被採納,這一路學到的東西也已經值回票價了。

如果你也是第一次遇到這種事

  • 告警一直重複出現又「修不好」,先懷疑是不是分類錯了。我們的告警本身沒壞,是它把兩種完全不同的問題混在一起了。
  • SDK 的原始碼沒有想像中可怕。我以前只敢看文件,這次被逼著點進去,發現關鍵的那段其實就十幾行。
  • 遇到不確定的設計問題,去看官方 SDK 怎麼做。官方把 SENDER_ID_MISMATCH 獨立出來是有原因的,那就是最好的參考答案。
  • workaround 可以先救火,但如果根源在上游,就把修正提回去。不然下一個用這個套件的人,還是會掉進同一個坑。
